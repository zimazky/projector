# План реализации учёта ресурсов по счетам

Дата: 1 ноября 2026 года; обновлено 2 ноября 2026 года. Основание: [концепция, редакция 4](multi_account_balance_proposal_2026-11-01_ru.md). Статус: выполнены R01–R07; результаты и статусы фиксируются ниже.

## 1. Назначение и результат

Документ задаёт порядок изменения приложения, зависимости, проверяемый результат каждого PR и условия перехода на новый формат. Поведение ресурсов, категорий, оценки и кэшбэка определено в концепции; здесь оно используется как требование, без повторного проектирования.

После выполнения плана приложение должно поддерживать:

- документные счета, ресурсы, единицы, категории счетов/ресурсов и категории кэшбэка;
- фактические движения по конкретным счетам и планы на счёт, категорию или без назначения;
- несколько сторон покупки/перевода/обмена, комиссии и обновление цены справочника при выполнении;
- прогноз количеств по счетам и категориям, общий итог в основной валюте и исключение категорий из него;
- месячные условия кэшбэка, сравнение карт, денежную или бонусную выплату на отдельный счёт;
- сохранение, восстановление и синхронизацию всего графа данных без потерь и повторных движений;
- удобные формы облигаций с ручной оценкой/НКД и материальных ресурсов.

Автоматические котировки, прогноз цен, расчёт купонных периодов/НКД, налоговый учёт, себестоимость по партиям, автоматическое распределение всех платежей месяца и банковские интеграции в этот план не входят. Купоны остаются обычными событиями по расписанию.

## 4. Правила безопасного перехода

До R09 новый путь развивается за одним внутренним флагом в точке сборки приложения либо в ветке функции. Продакшен по умолчанию продолжает читать и записывать прежний формат. Нельзя включить новую запись раньше готовности чтения, документных сторов, мапперов, расчёта и интерфейса.

В R03 новый codec тестируется отдельно от действующего публичного маршрута загрузки. До R09 документ новой версии через старый маршрут отклоняется с сохранением исходника, а не открывается в сторах, которые потеряют его поля. В интеграционных тестах новый путь можно включать полностью. На промежуточных PR приложение собирается и старые сценарии остаются работоспособными.

Для одного документа существует один записываемый источник операций. Во время перехода допустим адаптер старого отображения для одновалютных примеров, но не независимая запись одновременно в `credit`/`debit` и новые движения. Несопоставимые ресурсы не сворачиваются адаптером в одно число.

Открытие старого файла не перезаписывает его в Drive автоматически. Преобразование сначала проверяется на копии; исходный файл и исходный локальный снимок сохраняются. Первый переход требует определённой основной валюты: старый файл её не содержит, RUB — только предложенное значение. До выбора суммы можно просмотреть, но не сохранять их с неподтверждённой интерпретацией.

После записи нового формата выключение флага не является откатом данных. Для возврата к старой версии приложения используется сохранённый исходный снимок. Обратный экспорт с потерей ресурсов/счетов не выполняется автоматически. Версионные проверки должны остановить старый клиент до записи новых документов.

## 5. Содержание PR

### R01. Доменные контракты и арифметика

**Изменения.**

- Добавить модели единиц, ресурсов, категорий, счетов, цен, плановых целей, фактических движений и операций. Расположить предметные типы в `6-entities`, нейтральную десятичную арифметику — в `7-shared`.
- Зафиксировать результат оценки: сумма, валюта, версия набора цен, полнота и неоценённые позиции. Отсутствующая цена отличается от явного нуля.
- Определить каноническое представление `Decimal`, точность количеств/цен, округление денежных итогов и ограничения на чрезмерные значения. Масштаб единицы задаёт допустимый ввод, повышенная точность промежуточного расчёта сохраняется до установленной границы.
- Выбрать реализацию арифметики и закрыть её собственным небольшим интерфейсом. Конкретная зависимость выбирается при реализации по нужным операциям и совместимости сборки; весь домен не зависит от её API напрямую.
- Для ввода выражений определить десятичный путь, включая деление и поведение степеней; неподдержанное выражение получает понятную ошибку, а не переход к неточной арифметике.
- Зафиксировать в контрактах опциональный кэшбэк: категория покупки, расходные движения, месячные правила, ресурс/счёт получения, коэффициент начисления, единицы лимитов и связи выплаты.

**Затрагивается:** новые доменные модули; общий числовой слой рядом с `Calc`; `package.json`/lock при выборе зависимости. Публичный формат пока не меняется.

**Готово, когда:** проверены дробные суммы/литры, целые бумаги, деление, округление и ошибка недопустимого ввода; serialize/parse числа устойчивы; не требуется делать все существующие вычисления приложения десятичными в этом PR.

### R02. Идентичность событий и повторяемых вхождений

**Изменения.**

- Добавить постоянные `eventUid`, ID движений, `seriesUid` и ключ исходного вхождения. Временные числовые ID можно оставить для существующих UI-потребителей до их перевода.
- Сохранить UID при редактировании; копия получает новые UID и создаётся планом без фактических движений.
- Сохранять исходный план и происхождение выполнения/выделения повторения. При разбиении расписания сегменты сохраняют корректную связь с исходной серией.
- Определить восстановление отменённого выполнения: после Reload одно вхождение вновь планируется ровно один раз. Если исходная серия уже отредактирована, допустимо восстановить связанный одиночный план с исключением дубликата; нельзя слепо вернуть старую версию всей серии.
- Новые ID создаются командой создания/миграции, чтение и рендер их не генерируют повторно.

**Затрагивается:** `EventDto`, `IEventModel`, `SingleEventModel`, `RepeatableEventModel`, `EventMappers`, оба менеджера, `EventsStore`, `EventCacheStructure`. Новые поля сохраняет новый codec из R03; прежний writer до переключения не публикует их как новый формат.

**Готово, когда:** ID устойчивы при новом round-trip, правке, сохранении и загрузке; повторное выполнение одного ключа не дублирует факт; отмена одного вхождения не восстанавливает уже выполненные соседние вхождения.

### R03. Формат, миграция и сохранность снимков

**Изменения.**

- Подготовить документ v3 и сессию v4 с явной версией вложенного документа. Не ограничиваться увеличением констант: текущая логика проектов и вложенной версии зависит от конкретных старых значений.
- Разделить чтение версий: старый документ → существующая нормализация проектов → миграция ресурсов; новый документ → полная проверка нового графа.
- Расширить `DocumentData`: основная валюта, справочники, категории, текущие цены/журнал изменений, новые события, опциональные условия/снимки кэшбэка и связи выплат. Вычисляемые индексы, прогноз и кандидаты на карту в документ не записываются.
- Старые факты перевести на технический счёт, планы — в основной ресурс с целью `unassigned`. Оба ненулевых `credit` и `debit` сохраняются отдельными движениями. Создать категории по умолчанию и цену основной валюты 1.
- Миграция работает на копии; одинаковые исходники в одном контексте получают одинаковые ID, повторное чтение нового файла ничего не добавляет. Одинаковые по содержимому события не объединяются. Для файлов без происхождения создаётся сохраняемый контекст миграции.
- Проверять уникальность ID, типы категорий, ссылки движения/цены/кэшбэка, допустимые ресурсы счёта, коэффициенты, единицы лимитов и несовместимые комбинации плана/факта. Неизвестная версия отклоняется, новые поля не отбрасываются молча.
- Мигрировать локальные fingerprint/base-снимки консервативно. Их равенство допустимо утверждать только при сопоставимой нормализации и идентичности; при недоказуемом соответствии сохранять необходимость проверки сервера, а не помечать документ синхронизированным.
- Проверить `normalizeMainStoreData` в `DocumentTabsStore.utils`, сериализацию сессии, восстановление IndexedDB/localStorage и создание пустого документа. Новые блоки проходят все эти границы.

**Затрагивается:** `DocumentFormat`, новый мигратор/codec, `DocumentSessionFormat`, `DocumentTabsStore.types`, `DocumentTabsStore.utils`, персистентность, фикстуры и проверки восстановления.

**Готово, когда:** старые и новые файлы проходят чтение → нормализацию → запись → повторное чтение без потери данных; исходник неизменен; миграция не размножает сущности; неверная/будущая версия и потерянные ссылки не доходят до сторов. Публичное переключение остаётся за R09.

### R04. Документные справочники и единая публикация

**Изменения.**

- В `DocumentStoreManager` создавать и освобождать документные `AccountsStore`, `ResourcesStore`, категории и месячные условия кэшбэка. Встроенные единицы можно хранить общим неизменяемым каталогом; пользовательские данные принадлежат документу.
- Добавить доступ через провайдер документа, расширить `DocumentStores` и подготовку полного снимка. Не создавать глобальный изменяемый список счетов в `root`.
- Обобщить фиксацию изменений документа: правка ресурса, категории, цены или месячных условий должна сохраняться так же надёжно, как событие.
- Ввести пакетную публикацию команды: несколько изменённых сторов дают один итоговый снимок и один прирост `localVersion`. Инициализация/применение удалённого снимка не порождает ложную пользовательскую правку.
- Наблюдаемые версии справочников отделить от sync-версии. Правка неактивного документа остаётся привязанной к его `documentId`.

**Затрагивается:** `DocumentStoreManager`, его типы/callbacks, `DocumentTabsStore`, `root`/провайдер при необходимости; новые сторы.

**Готово, когда:** переименование/категория/цена/условия кэшбэка переживают Reload без изменения событий; две вкладки изолированы; замена удалённым снимком обновляет весь граф; одна составная команда не сохраняет промежуточные состояния.

### R05. Команды операций и атомарное обновление цены

**Изменения.**

- Ввести документный сервис команд для создания, выполнения, правки, отмены, удаления, переноса и копирования ресурсных событий. Команда получает явные `documentId` и стабильный UID/ключ вхождения.
- Сначала собрать и проверить новое состояние: счета, количества, все стороны, цена, комиссия, исходный план, будущая запись справочника и данные отмены. Только затем применить его одной публикацией.
- Учесть, что MobX action не откатывает исключение. Ошибка валидации не меняет ни событие, ни расписание, ни цену; применение подготовленного состояния не содержит сетевых ожиданий и частичных callback-сохранений.
- Разрешить много движений: например, деньги с карты A, бумага на брокерском счёте B, комиссия со счёта C. Одноресурсный перевод балансируется в своих единицах; разные ресурсы не проверяются общей суммой количеств.
- На покупке/обмене согласовать оплату, количество, цену и округление. Планы цену справочника не меняют. Включённая запись цены выполняется вместе с фактом, с ревизией и происхождением; поступление бонусов, купон и потребление цены не меняют.
- Реализовать защиту более поздней цены при правке/отмене сделки, заднюю/будущую дату и короткий журнал изменений. Не искать цену из операций при чтении документа.
- Начальные остатки и корректировки оформить командами, отдельно от доходов. Архивирование не удаляет остаток; используемые ссылки нельзя уничтожить.

**Затрагивается:** новый сервис команд, `EventsStore`/менеджеры, справочники и документная пакетная публикация. Интерфейс из R08 вызывает команды, а не вносит изменения в сторы по отдельности.

**Готово, когда:** все стороны проходят одной командой; ошибка на последней стороне оставляет прежнее состояние; двойное выполнение не добавляет факт; отмена/правка не оставляет старые движения и не затирает независимую цену. Локальная ошибка записи сохраняет видимые неподтверждённые изменения с повтором/экспортом через существующий механизм, не выдавая их за записанные на диск.

### R06. Остатки, прогноз, категории и оценка

**Изменения.**

- Реализовать `HoldingsIndex` по `(accountId, resourceId)` и `ForecastIndex` с тремя непересекающимися корзинами назначения.
- Применить формулы концепции: счёт содержит только назначенные ему планы; категория дополнительно учитывает свои планы без счёта; общий итог дополнительно учитывает `unassigned`.
- Выбирать точку прогноза явно, по умолчанию начало текущего местного дня. Факты сегодняшнего дня, будущие факты и оставшиеся планы учитываются по своим датам без повторного добавления; просроченное показывается отдельно.
- Сохранить счётчик повторений без полного разворачивания истории. Изменение временной зоны/текущей даты обновляет нужные производные значения в рамках существующего `DateTime`.
- `ValuationService` получает один неизменяемый снимок текущих цен. Меняются цены — пересчитывается оценка готовых количеств, а не история движений. Прошлые количества показываются в текущей оценке с подписью.
- Итог включает пересечение разрешённых категорий счёта и ресурса. `showInSummary` управляет строкой, не суммой. Две группировки не складываются друг с другом. Неполная оценка возвращается явно.
- Расширить ограниченные кэши и их зависимости. Старые методы агрегации документов не должны выдавать число из несопоставимых валют; до отдельного поддержанного сценария общий междокументный денежный итог недоступен с объяснением.

**Затрагивается:** `BalanceIndex`, `EventsCache`, `EventCacheStructure`, `OccurrenceCounter` при необходимости; новые индексы/оценка; DTO для календаря и списка дня.

**Готово, когда:** есть простая независимая контрольная реализация на небольших конечных наборах движений и сравнение с индексами; назначение плана внутри категории не меняет её итог; каждое движение учитывается один раз; смена цены/категории обновляет прогретый кэш. Сохраняются ограничения памяти и отсутствие обхода всех дней истории.

### R07. Справочники и настройка состава итога

**Изменения.**

- Добавить разделы счетов, ресурсов и категорий в существующую навигацию приложения. Готовые общие элементы форм переиспользовать; редакторы не хранят вторую копию всего доменного состояния.
- Реализовать создание/правку/архивирование счетов, допустимые ресурсы, цену ресурса и категорию. Добавить начальный остаток/корректировку через команды R05.
- Показать отдельные настройки «Включать в общий баланс» и «Показывать в сводке». Предупреждать о перегруппировке при смене категории и о планах, оставшихся без подходящего счёта.
- Поддержать бонусную программу как отдельный ресурс, бонусный счёт и исключение из денежного итога. Денежная цена бонуса необязательна.
- Сделать базовый редактор цены и происхождения; коэффициент начисления бонусов не помещать в этот редактор.

**Затрагивается:** новые страницы/редакторы в `3-pages`/`5-features`, `UIStore`, `App`, навигация, документные провайдеры.

**Готово, когда:** справочники можно подготовить без редактирования JSON; невозможны потерянные ссылки; страницы работают при отсутствии документа; изменение названия не меняет историю. Форма, открытая для документа A, не записывает данные в активированный затем B.

### R08. Карточка, календарь и список дня

**Изменения.**

- Заменить ввод `credit`/`debit` на простой приход/расход ресурса и редактор нескольких сторон для перевода/обмена. В строке плана — явный выбор цели «Счёт / Категория / Не выбрано».
- Сохранять контекст документа в `EventFormStore` вместе с UID и ключом вхождения; перед отправкой проверять, что исходная сессия ещё актуальна. Закрытая/заменённая сессия не должна принять запоздавшую форму.
- В выполнении требовать совместимые конкретные счета, показывать план и факт, цены и переключатель записи цены справочника. Все действия направлять в R05.
- Перевести календарь/список дня на результат R06: сумма с валютой, состав по категориям, количества, нераспределённые обязательства и отсутствие оценки. Не показывать пустую оценку как ноль.
- Сохранить существующие поиск, проекты, повторения, перенос и прокрутку. Проверить новые финансовые поля в поисковых/визуальных DTO, не скрывая движение многодневным плейсхолдером.

**Затрагивается:** `EventForm`/store, `CalendarStore`, `CalendarDay`, `CalendarEventItem`, `DayListStore`, `DayListEventItem`; e2e-селекторы и форматирование сумм.

**Готово, когда:** в браузере можно создать план на категорию, назначить карту, выполнить перевод/покупку, увидеть итог, отменить и восстановить всё после Reload. При переключении вкладки открытая форма не меняет чужой документ; правки не требуют `forceUpdate` и не прокручивают календарь неожиданно.

### R09. Переключение и выпуск основы

**Изменения.**

- Подключить codec v3 и снимок сессии v4 ко всем публичным точкам чтения/записи, импортам/экспорту и Drive. Удалить временные жёсткие подстановки версии вложенного документа.
- Выполнить проверенный переход на копии старых данных, с выбором исходной валюты и сохранением резервного источника. Не добавлять текущие полные остатки карт поверх уже учтённой истории; переход от технического счёта оформляется переносами/корректировками.
- Проверить конфликты, правку во время сохранения и закрытие вкладок. Применение загруженного снимка атомарно заменяет справочники, движения и цены. Прежние токены операций и проверка серверной версии остаются обязательными.
- Открывать новый путь по умолчанию только после полного прохождения проверок. Сохранить однонаправленное чтение старых форматов; старый писатель и временный адаптер удалить после устранения потребителей.

**Готово, когда:** старый файл, локальная старая сессия и новый файл проходят полную цепочку; после загрузки нет ложного dirty только от нормализации; миграция не подтверждает несуществующую серверную базу; редактирование во время save не помечается сохранённым ответом старого снимка.

### R10. Кэшбэк: чистый расчёт и ресурс выплаты

**Изменения.**

- Реализовать необязательные условия по паре счёт/месяц: повышенные/базовая ставки, минимальная покупка, лимит правила и общий лимит, валюта расчёта, ресурс и отдельный счёт получения.
- Процент рассчитывается от подходящей денежной суммы; коэффициент переводит результат в количество выплаты. Лимиты применяются в её единицах. Цена бонуса из справочника используется только для сравнения, не для начисления.
- Учитывать расходные стороны покупки, без автоматического включения перевода/комиссии/налога. Обычная покупка топлива может дать кэшбэк по денежной стороне обмена.
- Считать использованные лимиты по известным фактам и ранее назначенным планам с устойчивым порядком. План на категорию не резервирует все карты. Для кандидата исключать собственный прежний резерв, затем добавлять один гипотетический вариант.
- Различать отсутствие настроек, неподходящую категорию, исчерпанный лимит и неполные условия. Следующий месяц не наследует условия без явного копирования.
- Возвращать объяснение кандидата, количество выплаты, денежную оценку при наличии цены, ограничения по остаткам и неизвестные данные. Никаких записей в сторы при сравнении.

**Затрагивается:** новый `CashbackService` и месячный индекс; данные условий/снимков из R03–R04; контекст цен и прогноз R06.

**Готово, когда:** проверены пример 5% с достигнутым лимитом против 3%, 200 бонусов с независимой ценой 0,5 RUB, отсутствие цены, конкурирующие планы, повторения на границе месяца и покупка с несколькими картами. Смена цены бонуса не меняет его количество и использованный лимит.

### R11. Настройки кэшбэка, рекомендации и выплата

**Изменения.**

- Добавить месячный редактор условий счёта, категории кэшбэка и явное копирование на следующий месяц. Счёт получения бонусов может быть общим для нескольких карт той же программы.
- В карточке события показать подходящие карты, ожидаемые количества/оценки, лимиты и ограничения; выбор применяет конкретный счёт к расходной стороне. Окончательный выбор не подменяется автоматически при пересчёте.
- Ожидание показывается отдельно от фактического остатка и основного прогноза. По действию пользователя создаётся связанное плановое поступление нужного ресурса/цели на дату выплаты.
- При подтверждении фактического поступления требуется совместимый счёт и реальное количество; план заменяется фактом один раз. Поддержать одну выплату за несколько покупок и устойчивые связи на движения/вхождения. Повторная загрузка/подтверждение не создаёт второй приход.
- Сохранять снимок условий и ожидаемого начисления, отличая его от подтверждённого факта. Смена получателя в настройках не переносит уже назначенные поступления.

**Затрагивается:** редактор счёта/условий, `EventForm`, компоненты рекомендаций, команды связанных событий R05 и схемы ссылок R03.

**Готово, когда:** браузерный сценарий «покупка картой → ожидание бонусов → план на бонусный счёт → подтверждение → расход/обмен бонусов» проходит после Reload; остаток карты не увеличивается бонусами. Без настроек функция остаётся опциональной и обычное выполнение доступно.

### R12. Облигации и материальные ресурсы: удобные формы

**Изменения.**

- Добавить форму выпуска: идентификатор, количество в штуках, полная цена либо чистая цена/номинал/ручной НКД. Одна команда нормализует цену в справочнике и обновляет ревизию; НКД не прибавляется поверх полной цены.
- Добавить удобные формы покупки/продажи/погашения и покупки/потребления топлива поверх общих движений. При погашении уменьшается позиция бумаги, при амортизации номинал корректируется явно.
- Купон создавать обычным событием с расписанием. Показать ручной характер НКД и фиксированную оценку будущего; изменение числа бумаг не меняет сумму купонного события автоматически.
- Развести денежную покупку ресурса и последующее потребление в представлениях, чтобы один расход не учитывался дважды.

**Готово, когда:** проверены два выпуска с одной единицей, два топлива в литрах, покупка и расход топлива, чистая/полная цена, купон и погашение. Универсальное ядро при этом не содержит обязательного движка облигаций.

## 6. Сквозные инварианты для приёмки

| Инвариант | Контрольный пример |
| --- | --- |
| Каждое плановое движение имеет одну цель | 7 000 RUB на категорию не вычитаются ещё раз из общего «Не распределено» |
| Уточнение счёта внутри категории сохраняет групповой итог | План переносится с «Повседневных» на карту B; итог группы прежний |
| Оценка не меняет количество | Цена USD 90 → 95; 100 USD остаются 100 USD |
| Оценка берётся только из справочника | Чтение прогноза не выбирает последнюю сделку и не пишет новую цену |
| Выполнение заменяет план | Повторное нажатие и Reload не добавляют второе движение |
| Операция и её цена согласованы | Ошибка комиссии не оставляет выполненную покупку или обновлённый курс |
| Группировки не дублируют капитал | Подытоги счетов и ресурсов — две проекции, общий итог один |
| Кэшбэк не является деньгами заранее | 200 ожидаемых бонусов не меняют фактический остаток карты |
| Начисление независимо от оценки бонуса | Изменение цены бонуса меняет сравнение карт, но не 200 бонусов и не лимит |
| Получатель кэшбэка независим от плательщика | Расход RUB с карты, приход бонусов на отдельный счёт |
| Сохранение адресовано исходному документу | Форма A после перехода на вкладку B не меняет B |
| Отправленный снимок не меняется задним числом | Правка цены во время Drive-save остаётся новым несохранённым изменением |

npm run typecheck
