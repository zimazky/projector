# Исправление переполнения localStorage при миграции

Дата: 1 ноября 2026 года. Дополнение этапа 5, HEAD на старте — `d568142`. Основание — сообщение пользователя: QuotaExceededError при записи резервной копии перед миграцией, оценка неудавшейся записи 5,33 МиБ при уже сохранённых около 6,40 МиБ. Эти оценки характеризуют строки UTF-16, а не установленную квоту браузера. Состояние пользовательского браузера не читалось и не очищалось; проверки выполнялись с синтетическими данными в изолированном Chromium.

## Причина и изменение

Старый путь пытался сохранить полный архив прежней сессии в том же ограниченном localStorage. Повтор без изменения способа хранения не решал этот случай. Удаление старых document_* до успешной миграции сделало бы прежний снимок неполным, поэтому автоматическая очистка не добавлялась.

`LocalDocumentPersistence` теперь использует IndexedDB, если API доступен. База — `projector-documents`, версия 1; хранилища — `session` и `recovery`. Полная сессия со всеми вкладками находится в записи `session/current`. При первом переносе точные исходные строки localStorage архивируются в recovery, а новая сессия записывается в той же readwrite-транзакции. Подтверждением служит событие complete всей транзакции, а не успех отдельного put. Это соответствует [жизненному циклу транзакции IndexedDB](https://www.w3.org/TR/IndexedDB-3/#transaction-lifecycle).

Прежние ключи localStorage остаются нетронутыми. При запуске сначала читается IndexedDB; только отсутствие записи current допускает переход к старому формату localStorage. Невалидная или недоступная база не заменяется молча устаревшей копией. После успешного восстановления перенос запускается автоматически. Повторный запуск читает уже новый снимок и не создаёт повторный архив. Отсутствие IndexedDB API оставляет синхронный localStorage-путь; запрет доступа к существующей базе не включает такой fallback.

Записи сериализуются в момент команды и выполняются последовательно. Ошибка одной транзакции не блокирует следующие попытки. Подтверждение или ошибка устаревшей операции не меняет результат последней. Открытие базы и транзакции имеют ограничение ожидания; соединения закрываются. Сброс сессии записывает пустой снимок, а не удаляет current, чтобы старый localStorage не воскрес при следующем запуске. Архивы при сбросе сохраняются.

Восстановление IndexedDB асинхронное и не ждёт Google. До завершения чтения показан статус восстановления, создание/открытие других документов приостановлено. Явный сброс инвалидирует поздний ответ восстановления. Пока запись не завершена, виден статус «Сохраняется локальная копия…». При незавершённой или неудачной записи beforeunload предупреждает о закрытии страницы. Новые правки продолжают учитываться в памяти и могут быть экспортированы.

## Действия после обновления

1. Сохранить уже экспортированный `projector-session.json`; дополнительно скачать «Исходный снимок», если прежняя версия ещё открыта.
2. Загрузить обновлённую локальную версию приложения. Перенос выполнится автоматически; удалять данные сайта не требуется.
3. Дождаться исчезновения статуса локальной записи и проверить документы. Если последних правок нет, выбрать в меню «Импортировать сессию из файла» и открыть сохранённый `projector-session.json`.
4. Импорт добавляет восстановленные вкладки с суффиксом «(восстановлено)», сохраняя уже открытые. Прежде чем закрывать прежние вкладки, проверить восстановленное содержимое.

Импорт полностью проверяет файл и объединённый снимок до изменения доменных сторов. Неправильный архив не меняет сессию. Во время операций Drive импорт откладывается до их завершения. Действие не записывает данные на Drive. Экспорт исходного снимка включает и localStorage, и текущий снимок/архивы IndexedDB; такой архив предназначен для ручного восстановления, а пункт меню импорта принимает именно экспорт сессии.

## Проверки и ограничения

Проверены: Jest — 21 набор, 3632 теста; Chromium — 14 сценариев; типы приложения и E2E успешно; ESLint — 0 ошибок, 8 прежних предупреждений; production-сборка Pages — успешно, 14 файлов. Новые сценарии покрывают большую старую сессию с 2,4 миллионами символов в комментарии, запрет записи новых ключей документов в localStorage, сохранность точного архива, перезагрузку с последними правками, отмену транзакции после добавления архива и до записи сессии, повтор, а также импорт сохранённой сессии без удаления открытых вкладок. Проверки асинхронного стора покрывают поздние ответы, ошибки, сброс и блокировку открытия при восстановлении.

Результаты и хеши — в `indexed_storage_results_2026-11-01.json`; логи и полные JSON — `artifacts/indexed-storage`. Старые отчёты этапа 5 и диагностики относятся к прежним прогонам. Зависимости и lockfile не менялись, npm audit не повторялся. Публикация, коммиты и операции с настоящим Drive не выполнялись.

IndexedDB также может быть недоступен или исчерпать предоставленную браузером ёмкость; эти ошибки показываются с названием активного хранилища. Квота не обходится и не обещается неограниченное место. Запись остаётся полным сериализованным снимком, так что для очень больших историй ещё возможны затраты CPU/памяти. Межвкладочный совместный редактор и гарантированный offline-start ресурсов этим изменением не вводятся. При откате к старому коду он увидит старую копию localStorage; сначала нужно экспортировать текущую IndexedDB-сессию.

Дополнение: старые localStorage-записи после миграции можно убрать через [отдельную команду очистки](local_storage_cleanup_2026-11-01_ru.md), которая предварительно архивирует точные строки. Сам автоматический перенос по-прежнему не удаляет исходники.
