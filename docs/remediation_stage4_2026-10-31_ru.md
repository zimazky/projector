## Политика записи: отдельные версии файлов

**Изменённый документ сохраняется новым файлом Drive. Исходный файл не перезаписывается.** После подтверждения новая версия становится связанным файлом текущей вкладки. Другой клиент или старая общая ссылка продолжают обращаться к прежнему файлу; открыть новую версию можно через её имя в папке Drive.

Это выбранная политика разрешения гонки между проверкой и записью. Проверены [контракт files.update](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/update) и используемый GAPI-путь загрузки. Атомарное условие по ожидаемой `version` в интеграции не подтверждено; поддержка `If-Match` на реальном Drive не проверялась. Предварительное чтение metadata поэтому не объявляется compare-and-swap. Вместо зависимости от непроверенного условия записи используется предусмотренное планом сохранение отдельной копии.

Перед обычным сохранением обязательно читаются metadata исходного файла, независимо от TTL. При неизвестной базе или изменении серверной версии запись не начинается: команда возвращает контекст конкретного конфликта. Выбор локальной версии повторно проверяет этот контекст и создаёт отдельный файл; выбор удалённой версии читает согласованный снимок. Если удалённая версия снова изменилась, требуется новое решение.

Сам сервис записи также проверяет ожидаемую версию источника. Затем один [multipart POST](https://developers.google.com/workspace/drive/api/guides/manage-uploads#multipart) создаёт файл вместе с полным содержимым. Ответ этой операции подтверждает именно созданный файл и его `version`; дополнительное чтение metadata после записи не подменяет базу более поздней версией. В metadata копии записываются `appProperties.projectorSourceFileId` и `projectorSourceVersion`. Повторные сохранения заменяют собственный суффикс версии, а не наращивают его в имени.

Даже если исходный файл меняется после проверки, создание другого файла сохраняет обе стороны. Неизменённый документ после успешной проверки не создаёт лишнюю копию. «Сохранить как» при конфликте имени предлагает «Создать отдельную версию» или переименование; выбранный существующий файл сохраняется. Путь `GoogleApiService.updateFileContent` удалён. Старый низкоуровневый helper `GAPI.upload` остаётся вне команд записи документов; тесты проверяют, что эти команды его не вызывают.

Политика создаёт полные копии и не вводит общий указатель «последняя версия». Права новой копии определяются местом создания и не копируются с исходного файла. Если ответ создания потерян, локальный документ остаётся неподтверждённым: перед повтором нужно проверить папку Drive, где уже могла появиться копия.

## Серверная база и чтение

Metadata запрашиваются с `version`, `modifiedTime`, `headRevisionId`, `md5Checksum` и основными полями файла. [Drive определяет version как монотонную строку int64](https://developers.google.com/workspace/drive/api/reference/rest/v3/files). Она остаётся строкой, без потери точности через `Number`.

Маркер базы имеет вид `drive-v3:<fileId>:<version>`: ID задаёт принадлежность версии файлу, а равенство определяется также серверной `version`. `modifiedTime` используется для отображения; клиентские часы и `lastSyncAt` не определяют удалённый конфликт. Локальные версии, подтверждённая серверная база, свежесть проверки и операция остаются разными частями одной модели `sync`.

Открытие и pull выполняют `metadata → content → metadata`. Совпадение маркеров связывает содержимое с серверной версией. При смене маркера чтение повторяется, максимум две попытки; непрерывные изменения возвращают конфликт. Неполный JSON меняющейся версии не применяется. Перед изменением сторов проверяются структура документа, проекты и минимальный контракт EventDto: типы, реальные даты, время, длительность, конечные суммы и расписание. Неизвестные ошибки API нормализуются без обращения к отсутствующему `result.error`.

После загрузки локальная база использует сериализацию доменных сторов. Обычный check загружает только metadata и не меняет содержимое или локальную версию из-за нормализации необязательных полей DTO. Токены и локальные версии этапа 3 продолжают защищать применение ответов; новые правки во время pull сохраняются.

После перезапуска операция сбрасывается, связанный файл требует проверки, время проверки сбрасывается. Старый file ID или timestamp в поле ревизии не признаётся серверной базой. До подтверждения нет `synced`; неизвестная база требует решения пользователя. Пакетная проверка выбирает документы по `sync.needsRemoteCheck`, включая восстановленные dirty-документы.

## Координатор и UI

`DriveSyncCoordinator` запускается при монтировании приложения. Он проверяет связанные документы после входа, при активации вкладки, появлении связанных документов и возврате сети. Интервал обслуживания — 30 секунд, TTL metadata — 60 секунд. Запросы одной сессии дедуплицируются; фон не открывает OAuth и не вытесняет пользовательскую операцию. Ошибка не запрещает редактирование и повторную попытку.

`dispose` освобождает reaction, таймер и обработчики online/offline, а также инвалидирует принадлежащие координатору незавершённые проверки. Поздний ответ после dispose не подтверждает документ. Размонтирование приложения вызывает остановку через `MainStore`.

`DocumentTabs`, `Header`, `CalendarIconBar`, `ConflictDialog` и подтверждение закрытия используют единый `DocumentUiState`. Различаются локальные изменения, другая удалённая версия, конфликт, неизвестная актуальность, операция и ошибка. Маркер локальных изменений не скрывается ошибкой. Вкладка и заголовок имеют одинаковый `data-sync-status` и tooltip из селектора. Команда сохранения называется «Сохранить новую версию»; результат сообщается небольшим закрываемым уведомлением. Legacy-поля остаются проекцией для совместимости snapshot, счётчиков и последующего удаления.
