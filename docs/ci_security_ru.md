# Проверки CI и аудит зависимостей

Workflow `.github/workflows/build.yml` проверяет pull request, push в любую ветку и ручной запуск. Используется обычный `pull_request`; PR собирается с тестовыми значениями переменных Google/погоды. Секреты сборки подключаются только при push в `master`. Правила событий основаны на [документации GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request).

Две независимые задачи:

- `build`: `npm ci --no-audit`, тесты инструментов CI, типы приложения/e2e, линтер, Jest, Chromium и production-сборка с проверкой состава Pages.
- `audit`: `npm ci --ignore-scripts --no-audit`, затем `npm run audit:ci` для полного и production-дерева.

`deploy` зависит от успеха обеих задач и запускается только для push в `master`. Загрузка артефакта Pages также выполняется только для этого события. Каталог публикации — `artifacts/pages`; отчёты аудита хранятся отдельно. Права `pages: write` и `id-token: write` выделены только задаче deploy; остальные задачи имеют `contents: read`, согласно [принципу минимальных прав GitHub Actions](https://docs.github.com/en/actions/tutorials/authenticate-with-github_token).

Чтобы запрещать слияние PR с ошибками проверок, в настройках защиты ветки нужно сделать `build` и `audit` обязательными статусами. Сам workflow защищает свой deploy; настройки защиты ветки этим изменением не менялись.

## Локальный запуск

```powershell
npm ci --no-audit
npm run test:ci
npm run typecheck
npm run typecheck:e2e
npm run lint-check
npm test -- --runInBand
npm run browser:install
npm run test:e2e
npm run build:pages
npm run audit:ci
```

Для локальной интеграции с Google/погодой используется `.env`, созданный из `.env.example`. В примере значения пустые. Для проверки сборки без интеграций можно задать `CLIENT_ID=ci-placeholder` и `OPEN_WEATHER_KEY=ci-placeholder` через переменные окружения.

## Результаты аудита

`npm run audit:ci` запускает npm audit отдельно для полного дерева (включая dev) и для production (`--omit=dev`). CLI npm вызывается через Node без shell. Каждый процесс ограничен 60 секундами; сетевой запрос npm — 15 секундами и одной повторной попыткой. Команда не обновляет пакеты/lockfile и не запускает audit fix.

До применения политики сохраняются:

| Файл в `artifacts/audit` | Содержимое |
| --- | --- |
| `full.json`, `production.json` | Исходный stdout соответствующего npm audit |
| `full.stderr.log`, `production.stderr.log` | Диагностика npm |
| `summary.json` | Статусы, команды, npm exit code, длительности, счётчики, конкретные находки, исключения и SHA-256 lockfile/политики |

Оба режима выполняются и сохраняются даже при отказе первого, некорректной политике или lockfile. При пустом/повреждённом ответе файл сохраняет именно этот сырой ответ; такой `.json` может быть пустым либо невалидным. `summary.json` обозначает ошибку, а не чистый аудит.

Код 1 самого npm при найденных уязвимостях ожидаем. [npm audit-level влияет на exit code, но не фильтрует JSON-отчёт](https://docs.npmjs.com/cli/v11/commands/npm-audit/#description). Поэтому CI проверяет содержимое отчёта, его схему, ссылки между метауязвимостями, счётчики и соответствие путей установленным версиям lockfile. Пустой ответ, npm error, таймаут, неизвестная схема и противоречивый отчёт завершают проверку ошибкой.

В сводке `auditStatus` различает `clean`, `advisories` и `error`. Отдельный `status` означает решение политики: `passed`, `blocked` либо `error`. `passed` с `advisories` не означает отсутствия уязвимостей: moderate/low остаются видимыми в отчёте.

Коды завершения `audit:ci`:

- **0** — оба отчёта корректны, политика допускает находки;
- **1** — есть high/critical без подходящего исключения;
- **2** — получение, сохранение или проверка отчётов/политики не завершились корректно.

В Actions задача загрузки `dependency-audit` выполняется также после ошибки аудита и сохраняет отчёты на 14 дней. При отмене workflow загрузка не гарантируется. Браузерные отчёты сохраняются отдельно на 7 дней.

## Политика и исключения

`security/audit-policy.json` содержит схему версии 1 и массив `exceptions`. Сейчас массив пуст: разрешённых high/critical нет. Исторический отчёт `docs/remediation_stage2_remaining_2026-10-31.json` описывает moderate/low и не служит списком разрешений CI.

Решение принимается по конкретной комбинации **scope + package + advisory + path + version + severity**. Числовой baseline не используется. Исчезновение одной advisory не разрешает другую, даже если общее число находок осталось прежним. При отсутствии GHSA в URL используется стабильный ID `npm:<source>` из отчёта. Метауязвимость родителя связывается с исходной advisory; разрешение для leaf-пакета не распространяется на родителя или другую установленную копию.

Пример структуры одного вымышленного исключения, которое не нужно добавлять в рабочую политику:

```json
{
  "scope": "full",
  "package": "example-package",
  "advisory": "GHSA-aaaa-bbbb-cccc",
  "path": "node_modules/example-package",
  "version": "1.2.3",
  "severity": "high",
  "owner": "Projector maintainer",
  "reason": "Описание применимости, ограничений и причины временного исключения",
  "expiresOn": "2026-11-14"
}
```

Для production требуется отдельное исключение со scope `production`. Диапазоны версий, маски, дубликаты, отсутствие ответственного/обоснования и просроченные записи не принимаются. `expiresOn` — дата UTC: в этот день исключение уже недействительно, даже если находка исчезла. Исключение требует адресного изменения с обоснованием и датой пересмотра; автоматически из отчёта оно не создаётся.

## Состав Pages

`build:pages` собирает JS/CSS отдельно и запускает `scripts/package-pages.mjs`. Упаковщик копирует только index и явно разрешённые ресурсы, проверяет уже существующий каталог и отклоняет лишние файлы/каталоги и символические ссылки в результате. Тесты `test:ci` проверяют, что отчёт аудита не копируется в публикацию и что его появление внутри Pages останавливает упаковку.
