# PR 12 — стабильные проекты и миграция ссылок

Дата: 1 ноября 2026 года, Europe/Moscow. Второй отдельный шаг этапа 6 [плана исправлений](remediation_plan_2026-10-31_ru.md), проблема F11. Реализовано локально; коммит, удалённый PR и публикация агентом не выполнялись.

## Поведение

Раньше события хранили индекс проекта в массиве, а при сохранении записывали его имя. После удаления более раннего проекта индекс указывал на другую запись; после переименования в событиях сохранялось прежнее имя. Счётчик использований увеличивался при добавлении, но не уменьшался при удалении и замене события.

Теперь проект имеет неизменяемый строковый `id`, а событие — `projectId`. В рабочих моделях одиночных и повторяемых событий прежнее имя проекта удалено. Стиль определяется по ID через `Map`, независимо от порядка списка. Переименование меняет только отображаемое имя. Новые проекты получают отдельные ID; повторное создание удалённого проекта с таким же именем не присваивает ему прежние ссылки. Служебный проект имеет зарезервированный ID `default`, его объект и счётчик независимы у каждого документа.

Редактирование, удаление и значения выпадающего списка проектов адресуются по ID. Редактор также захватывает исходную сессию: открытая форма не применяется к другой вкладке с совпадающим ID проекта. Подтверждение удаления связано с исходным хранилищем. Поиск по имени остаётся только для выбора отображаемого проекта и приёма старого входного DTO; явный неизвестный ID отклоняется.

Счётчик хранит число ссылок от записей одиночных событий и повторяемых серий, а не число календарных вхождений. Добавление, удаление, смена проекта, complete/undo, copy, reset и разбиение серии обновляют его согласованно до уведомления потребителей. После удаления последней записи проекта счётчик равен нулю и проект можно удалить. Проверено разбиение в последний день серии с исключающей конечной датой.

## Форматы и миграция

- Документ Drive — `schemaVersion: 2`: `projectsList[].id` и `projectId` у каждого события, включая `default`. Имя проекта в событие больше не записывается.
- Снимок и экспорт сессии — `schemaVersion: 3`. Внутри каждой вкладки данные имеют тот же контракт ссылок, что и документ v2, без отдельной вложенной версии. Версия базы IndexedDB остаётся 1.
- Документы без версии и v1 мигрируют на новой структуре. ID старого проекта детерминированно получается обратимым кодированием имени с префиксом `legacy:`. Короткий хэш не используется. Новые ID после миграции не меняются при переименовании.
- Проверяются пустые, повторяющиеся и зарезервированные ID, отсутствующие ссылки, а также противоречащие друг другу старое имя и новый ID. Неполный документ не применяется к текущей сессии. Прежняя политика восстановления неизвестного имени проекта из безверсионного документа сохранена; повреждённая ссылка v1 отклоняется. Неоднозначную историческую принадлежность приложение не угадывает.
- Сессии без версии/v1/v2 мигрируют в v3. Точные JSON-отпечатки локального содержимого и базы переводятся в тот же контракт ID; известные clean/dirty сохраняются. Короткий или непрочитанный отпечаток не доказывает известную базу; неизвестная база остаётся неизвестной. Связанные документы по-прежнему требуют проверки Drive после восстановления.
- Перед первой перезаписью старый localStorage-снимок резервируется в отдельный ключ. Старый IndexedDB `current` архивируется вместе с записью v3 в одной транзакции. Отказ оставляет оригинал без частичного архива; повтор сохраняет его один раз. Повторное открытие v3 не создаёт новый архив миграции.

Запись Drive продолжает использовать проверку версии и условный PUT с `If-Match`, сохраняя тот же ID файла и создавая новую серверную ревизию. Транспорт и политика разрешения конфликта S01 не менялись. Старый файл читается без автоматической записи; формат v2 записывается при сохранении пользователем.
