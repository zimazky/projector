# S01 — сохранение в тот же файл Drive

Дата: 1 ноября 2026 года, Europe/Moscow. Продолжение [плана исправлений](remediation_plan_2026-10-31_ru.md) после [удаления legacy (PR 10)](remediation_pr10_2026-11-01_ru.md). Реализовано локально; условная запись проверена пользователем на настоящем Google Drive через подготовленную страницу. Публикация и коммит агентом не выполнялись.

## Поведение

Открыть `data.json` → изменить → «Сохранить»: изменяется содержимое того же файла. Его ID, имя, папка и ссылка сохраняются; новый файл с суффиксом версии не создаётся. Повторное сохранение работает с тем же ID. «Сохранить как...» сохраняет прежний путь создания отдельного файла, включая отдельную копию при конфликте имени.

Файлы «(версия …)», созданные до S01, остаются текущими связанными файлами. Обычное сохранение обновляет именно их. Другой исходный файл можно открыть явно через выбор файла; автоматического поиска прежнего оригинала, удаления версий или смены целевого ID нет.

## Протокол записи

1. `DocumentTabsStore` захватывает исходную сессию, токен, локальную версию и неизменяемый отправляемый снимок. Команды по ID и дедупликация записей одной сессии сохранены.
2. Metadata Drive v3 проверяются перед каждой записью. Неизвестная серверная база требует решения пользователя. Если известная `version` изменилась, обычное сохранение согласованно читает `metadata → content → metadata` и точно сравнивает данные с известной базой в сериализации доменных сторов. Только совпадение позволяет принять служебную смену версии без диалога; локальное содержимое не заменяется. При отличии данных возвращается конфликт. Уже принятое решение пользователя не переиспользуется для новой серверной версии.
3. `GoogleApiService.updateFileContent` получает `version` и сильный `etag` одним запросом Drive v2. Версия должна совпасть с проверенной базой. Запись — `PUT /upload/drive/v2/files/{fileId}?uploadType=media` с `If-Match`, `newRevision=true` и `updateViewedDate=false`. Имя, папка и права в запрос не передаются. Без ETag, с wildcard или слабым ETag запрос не отправляется.
4. Изменение файла между чтением и PUT отклоняется сервером с HTTP 412. Приложение читает свежие metadata и возвращает новый конфликт; безусловного повтора нет. Выбор локальных данных относится к конкретной проверенной версии и обновляет этот файл только с новым условием записи.
5. Базу подтверждает ответ самой записи: проверяются ID и возрастающая строковая int64-версия. Поздний GET не подменяет версию отправленного снимка. Локальные правки в полёте остаются dirty. После закрытия/замены сессии устаревшее продолжение не начинает новый PUT и не подтверждает другую вкладку.
6. Неопределённый сетевой результат или неверный ответ не считаются успехом. Вкладка и локальные данные сохраняются; следующая попытка снова проверяет Drive. Низкоуровневый безусловный `GAPI.upload` удалён.

Документация Google описывает [ETag и version в v2 File](https://developers.google.com/workspace/drive/api/reference/rest/v2/files), [endpoint обновления и updateViewedDate](https://developers.google.com/workspace/drive/api/reference/rest/v2/files/update), а [таблица v2/v3](https://developers.google.com/workspace/drive/api/guides/v2-to-v3-reference) отмечает отсутствие поля etag в v3. Поэтому условная запись изолирована в v2, а чтение и модель документа продолжают использовать v3. Работоспособность `If-Match` не выведена из одного предварительного GET: отказ устаревшего PUT проверен на настоящем сервере.

## Живая проверка

Пользователь запускал `scripts/verify-drive-write.mjs` в своём браузере с реальной авторизацией. Итоговый отчёт находится в `artifacts/drive-write-live/result.json`; копия включена в [структурированные результаты](remediation_s01_results_2026-11-01.json). Токены и содержимое пользовательских документов в отчёт не попадают. Проверка использует только создаваемые ею тестовые файлы.

Подтверждены: согласованность версий v2/v3 на стабильном файле; обновление того же ID; HTTP 412 для устаревшего ETag после конкурентной записи; сохранность данных другого клиента; отказ сервиса по старой версии; обычное и повторное сохранение; чтение результата через v3; два экземпляра `DocumentTabsStore`, обнаружение изменения вторым клиентом и повторное сохранение первым; сохранение имени и ID; отдельный файл через «Сохранить как». Тестовые файлы перемещены в корзину, ошибок очистки нет.

Проверка выявила служебное изменение `version` после операций Drive при неизменном содержимом. Это устранено точным сравнением с известной базой, а не безусловным продвижением маркера после GET. Предварительные неуспешные прогоны сохранены в `artifacts/drive-write-live/result-attempt*.json`; успешная транспортная проверка и заключительная проверка команд различаются в отчётах.

Отдельные тесты покрывают сильный ETag, запрет незащищённой записи, HTTP 412, пропавший ответ, неверные metadata, int64 без округления, закрытую сессию до PUT, два клиента, известную/неизвестную базу и служебную версию, правки в полёте и сохранность вкладки при закрытии. Chromium проверяет путь UI → команда → сервис → условный HTTP-запрос, повторное сохранение, гонку перед PUT, явное разрешение конфликта и отдельный файл через «Сохранить как».

Итог: **Jest — 3682 теста в 23 наборах; Chromium — 25 сценариев, без ошибок и повторов; ESLint — 0 ошибок и 8 прежних предупреждений; обе проверки типов и production-сборка успешны.** Подробные счётчики и хеши — в [JSON результатов](remediation_s01_results_2026-11-01.json).
