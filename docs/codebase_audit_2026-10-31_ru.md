# Аудит Projector — 31 октября 2026 года

## 1. Общая оценка

Проект можно развивать на существующем стеке. React, TypeScript, MobX, CSS Modules и разделение доменной модели, DTO и представления подходят для такого приложения. Главная проблема сейчас — надёжность жизненного цикла документов: часть операций использует новую модель синхронизации, часть продолжает изменять старые флаги, а асинхронные действия часто привязаны к активной вкладке вместо конкретного документа.

**До активного использования с важными данными следует исправить ошибки сохранения и закрытия документов.** Найдены пути потери локальных изменений, ошибочного назначения файла другой вкладке и незаметной перезаписи удалённой версии. Успешная сборка и большое число тестов эти сценарии сейчас не гарантируют.

Рекомендуется последовательное исправление существующего приложения. Переписывание на другой фреймворк, обязательная замена MobX или переход на серверный рендеринг не следуют из обнаруженных проблем.

## 5. Ошибки сохранения и синхронизации

### F01. «Сохранить и закрыть» может удалить несохранённые данные

**Место:** [App.tsx](../src/1-app/App/App.tsx), строки 45–64; [DocumentTabsStore.ts](../src/6-entities/Document/model/DocumentTabsStore.ts), `saveActiveDocument`, `closeDocument`.

При выборе «Сохранить» обработчик вызывает `saveActiveDocument().then(() => closeDocument(docId))`. Возвращаемый `boolean` игнорируется. Метод сохранения возвращает `false` при ошибке, а для нового документа без `fileId` сразу возвращает `false`. Затем `closeDocument` удаляет и сессию, и запись содержимого в `localStorage`.

**Сценарий:** создать документ, добавить событие, закрыть вкладку крестиком и выбрать «Сохранить». У документа ещё нет `fileId`, сохранение не выполняется, вкладка всё равно удаляется. Аналогичный исход возможен при сетевой ошибке существующего файла.

Дополнительно `requestUnsavedDecision` создаёт Promise, но `resolveUnsavedDecision` не вызывает сохранённый `resolver`. Ожидание в `handleClose` не завершается. Сейчас закрытием занимается другой обработчик, что маскирует нарушение контракта.

**Исправление:** единая команда `requestCloseDocument(documentId)` с последовательностью «решение → сохранение/Сохранить как → проверка результата → закрытие». Закрывать только после подтверждённого успеха либо явного «Не сохранять». Отмену и ошибку возвращать отдельными исходами; Promise решения всегда завершать.

### F02. Разрешение конфликта имени файла не работает

**Место:** [SaveToDriveStore.ts](../src/4-widgets/SaveToDrive/model/SaveToDriveStore.ts), строки 52–55, 128–161, 165–169.

`resolveConflict` сначала вызывает `closeConflictDialog`, который очищает `conflictingFiles` и `newFileNameForConflict`. Затем обработчик пытается прочитать уже очищенные значения.

**Локальный результат:** при заранее заданном конфликтующем файле вариант `overwrite` возвращает «Нет файла для перезаписи.», а `rename` с непустым новым именем — «Новое имя файла не может быть пустым.».

**Исправление:** сначала зафиксировать выбранный файл и новое имя в локальных переменных либо объекте команды, выполнить выбранную операцию и только затем очищать состояние. Добавить проверки отмены, перезаписи, переименования и повторной ошибки сети.

Дополнительный дефект: `generateUniqueFileName` для имени без расширения теряет основу имени, поскольку `nameWithoutExt` получается из пустого `nameParts`. Например, для `Calendar` кандидат будет ` (1)`. Список конфликта содержит только совпадения исходного имени и не гарантирует уникальность следующего кандидата.

### F03. Проверка версии на Drive фактически не защищает от перезаписи

**Место:** [gapi.ts](../src/7-shared/services/gapi.ts), строки 281–285; [DocumentTabsStore.ts](../src/6-entities/Document/model/DocumentTabsStore.ts), строки 197–204, 398–404, 492–498, 565–573; [GoogleApiService.ts](../src/7-shared/services/GoogleApiService.ts), строки 219–223.

Обнаружены связанные ошибки:

1. `getFileMetadata` запрашивает только `id, name, mimeType, parents, iconLink, webViewLink`. Поля `modifiedTime` в ответе не будет, хотя синхронизация сравнивает его с локальным временем. При отсутствии поля используется 0, и признак `hasRemoteChanges` становится ложным.
2. `baseRevisionId` и `remoteRevisionId` получают `metadata.id`. Это идентификатор файла, сохраняющийся при изменении содержимого, а не идентификатор версии.
3. Даже после добавления `modifiedTime` сравнение с клиентским `Date.now()` ненадёжно: часы клиента и сервера могут расходиться. После первого открытия `lastSavedAt` вообще остаётся `null`, что даст ложное «удалённая версия новее».
4. Обычное сохранение существующего файла сразу выполняет PATCH содержимого. Проверка удалённой версии и подтверждение реального конфликта не являются обязательной частью этой операции.

**Последствие:** файл, изменённый на другом устройстве, может быть перезаписан без корректного предупреждения.

**Исправление:** хранить серверную базовую версию, возвращать необходимые поля в метаданных и сравнивать удалённое состояние с базой, относительно которой пользователь редактировал документ. Для JSON-файлов рассмотреть `version`/`headRevisionId` с учётом их семантики. Перед перезаписью проверять ожидаемую версию; отдельно спроектировать защиту промежутка между проверкой и записью. Простая предварительная проверка сама по себе не делает запись атомарной.

Семантика полей описана в [Drive API v3: Files](https://developers.google.com/workspace/drive/api/reference/rest/v3/files), а выбор полей — в [руководстве Google](https://developers.google.com/workspace/drive/api/guides/search-files). Это основание для рекомендации; атомарный протокол записи с конкретным API в рамках аудита не реализовывался.

### F04. Правки во время сохранения не попадают в снимок и перестают считаться изменениями

**Место:** [DocumentTabsStore.ts](../src/6-entities/Document/model/DocumentTabsStore.ts), строки 332–364, 386–417, 424–447; [MainStore.ts](../src/1-app/Stores/MainStore.ts), обработчики изменений сторов.

`updateActiveDocumentData` полностью выходит при `isSaving === true`. При этом события в доменном `EventsStore` продолжают изменяться. Данные сессии и локальный снимок отстают от доменного состояния, а по завершении сохранения `markDocumentSavedToDrive` сбрасывает `isDirty`.

**Локальное воспроизведение с задержанным Promise сохранения и callback как в MainStore:** перед сохранением было одно событие; во время запроса добавлено второе. В `EventsStore` стало 2 события, в `session.data` осталось 1, после успешного ответа `isDirty === false`. Перезагрузка или закрытие могут потерять второе событие.

**Исправление:** не прекращать фиксацию локальных изменений во время сетевой операции. В начале сохранения захватывать неизменяемый снимок и его локальную версию. После ответа двигать базу только до отправленного снимка. Если документ изменился после начала запроса, он должен остаться dirty. Предусмотреть очередь/дедупликацию параллельных сохранений одного документа.

### F05. Операции нужно адресовать документу, а не текущей вкладке

**Место:** [SaveToDriveStore.ts](../src/4-widgets/SaveToDrive/model/SaveToDriveStore.ts), строки 28–35 и 90–101; [CalendarIconBar.tsx](../src/4-widgets/CalendarIconBar/CalendarIconBar.tsx), `handleChooseRemoteVersion`; [DocumentTabsStore.ts](../src/6-entities/Document/model/DocumentTabsStore.ts), строки 456–463 и `openFromDrive`.

«Сохранить как» хранит содержимое, но не ID исходного документа. После ответа API обработчик берёт `activeDocument` и присваивает ему полученные метаданные.

**Локальный результат:** открыть «Сохранить как» для A, активировать B и завершить сохранение. У A `fileId` остался `null`, а B получил `file-a`. Файл содержит снимок A, но связан с B. Также правки, сделанные после открытия диалога, могут ошибочно считаться сохранёнными: в диалоге остаётся старое содержимое, а базовый fingerprint вычисляется по текущей сессии.

Другие проявления того же подхода, подтверждённые кодом:

- `saveActiveDocument` в `catch` ищет сессию по **текущему** `activeDocumentId`, а не по ID начавшего запрос документа. Ошибка может попасть в другую вкладку, исходная останется `isSaving`.
- Выбор удалённой версии скачивает содержимое, затем вызывает `applyContentToActiveDocument`. При смене активной вкладки между этими действиями содержимое может примениться к другому документу.
- Если закрыть документ во время `openFromDrive`, продолжение запроса использует `this.state.documents.get(id)!`; обработчик ошибки повторяет такое же предположение. Наличие сессии после `await` не гарантировано.

**Исправление:** каждая команда должна нести `documentId`, снимок/локальную версию и `operationToken`. После `await` проверять существование документа и актуальность операции. Все ветви успеха и ошибки адресовать исходному ID. В модели `operationToken` уже объявлен, но защиты перечисленных операций не обеспечивает.

### F06. Fingerprint даёт коллизии на обычных названиях

**Место:** [DocumentSyncFingerprint.ts](../src/6-entities/Document/model/DocumentSyncFingerprint.ts), `simpleHash`; [DocumentSyncSelectors.ts](../src/6-entities/Document/model/DocumentSyncSelectors.ts), `getIsDirty`.

Равенство 32-битных хэшей используется как доказательство отсутствия изменений. Это уже даёт простой воспроизводимый сбой: два одинаковых документа с единственным событием, называющимся соответственно `Aa` и `BB`, получают один fingerprint — `30aa05af` при дате события `2026.10.31` и пустых остальных списках.

После сохранения версии `Aa` переименование в `BB` может быть признано отсутствием изменений. Хэш теряет ещё часть пространства значений из-за `Math.abs`.

**Исправление:** для dirty-tracking использовать локальную монотонную версию либо точное сравнение канонического снимка с базой. Если нужен именно отпечаток содержимого — применять подходящий устойчивый digest, сохранив проверку актуальности асинхронного вычисления. Не возвращать псевдослучайный fingerprint при ошибке сериализации: ошибка должна обрабатываться явно.

Также `WeakSet` в replacer считает любую повторную ссылку циклом, даже если структура не циклическая. Это не основной воспроизведённый дефект, но ещё одна причина закрепить контракт: fingerprint должен зависеть от сериализуемого содержимого, а не от совместного использования ссылок.

### F07. Локальная сессия не восстанавливается без Google API

**Место:** [MainStore.ts](../src/1-app/Stores/MainStore.ts), строки 81–96.

Вызов `restoreFromLocalStorage` стоит внутри `.then()` после `waitForGapiReady()`. Если загрузка скриптов Google недоступна или инициализация отклонена, восстановление не вызывается; ошибка только выводится в консоль.

**Последствие:** локально сохранённые документы не появляются в сценарии, где они особенно нужны — без доступа к Google. Это ограничение запуска и восстановления; оно не доказывает, что приложение целиком умеет стартовать без сети: для этого нужна отдельная проверка кеширования собственных ресурсов.

**Исправление:** сначала восстановить локальную сессию независимо от Google, затем отдельно инициализировать Drive и предложить проверку удалённых версий. Ошибку внешнего сервиса показывать как ограничение внешних операций, а не прерывать локальный сценарий.

### F08. После перезапуска показывается неподтверждённый статус «синхронизировано»

**Место:** [DocumentTabsStore.ts](../src/6-entities/Document/model/DocumentTabsStore.ts), строки 240–264, 757–800 и `syncAllDocumentsWithDrive`; [DocumentSyncSelectors.ts](../src/6-entities/Document/model/DocumentSyncSelectors.ts), `getUiSyncStatus`, `syncLegacyStateFromNewModel`.

`openFromLocalStorageSnapshot` выставляет `offline`, но при загрузке данных `syncLegacyStateFromNewModel` может заменить статус на `synced` только по равенству локального и базового fingerprint. Если в снимке уже есть `sync`, `needsRemoteCheck` принудительно не устанавливается.

**Локальный результат:** восстановленный ранее сохранённый документ получил `syncStatus: 'synced'` и `needsRemoteCheck: false` без единого обращения к Drive. `syncAllDocumentsWithDrive` выбирает только документы со статусом `offline` и такой документ пропускает.

Дополнительно восстанавливается старый `state.isSaving`, хотя сама операция сбрасывается в `idle`: после перезапуска признак незавершённого запроса может продолжать блокировать обновления.

**Исправление:** разделить равенство локальной версии базе и свежесть удалённой проверки. При новом запуске помечать связанные файлы как требующие проверки; не выводить подтверждённую синхронизацию до неё. Сбрасывать все временные состояния загрузки/сохранения. Согласовать условия пакетной синхронизации с новой моделью.

## 6. Данные, поиск и вычисления

### F09. JSON и локальные снимки недостаточно проверяются

**Место:** [DocumentTabsStore.types.ts](../src/6-entities/Document/model/DocumentTabsStore.types.ts), `parseDocumentContent`, `parseDocumentTabsSnapshot`; [DocumentTabsStore.utils.ts](../src/6-entities/Document/model/DocumentTabsStore.utils.ts); [DocumentTabsStore.ts](../src/6-entities/Document/model/DocumentTabsStore.ts), строки 703–800.

`parseDocumentContent` только приводит значение к типу через `as`. Нормализатор проверяет проекты и наличие массивов событий, но сами события тоже приводит через `as`. Обычный путь открытия Drive использует первый парсер, а выбор удалённой версии — другой, то есть входные контракты различаются. Восстановление `localStorage` также доверяет структуре данных и ссылкам между `documentOrder`, `documents` и `activeDocumentId`.

Неверное поле `start`, `null` вместо события или некорректное расписание могут дойти до мапперов и вычислителей. Ряд ошибок загрузки оставляет частично изменённую сессию.

Записи `localStorage.setItem` выполняются без обработки отказов. Квота или запрет хранилища способны прервать обработчик уже после изменения памяти; метаданные и содержимое записываются разными операциями. Нет версии формата, транзакции или стратегии восстановления неполной записи. Изменения всего документа сериализуются синхронно при редактировании.

**Исправление:** один runtime-валидатор входного формата с `schemaVersion` и миграциями для Drive и локального хранения; проверка каждого EventDto, календарной даты, конечных чисел и расписания. Сначала проверить новый снимок, затем атомарно заменить доменное состояние. Вынести хранение в адаптер с явными результатами ошибок. Для объёмных документов рассмотреть транзакционный IndexedDB и отложенную запись с надёжным завершением; не ограничиваться увеличением квоты.

### F10. Пагинация поиска пропускает события одного дня

**Место:** [EventSearchStore.ts](../src/5-features/EventSearch/EventSearchStore.ts), строки 114–115, 316–360, 365–410.

Курсор содержит только `timestamp`. После выбора первых четырёх совпадений следующая порция ищет строго `event.start > latestFound`, а предыдущая — строго меньше `earliestFound`. Остаток результатов на граничной дате теряется.

**Локальный результат:** создано 6 одиночных событий на сегодня с одинаковым поисковым словом. После поиска и многократного `nextResult()` доступны только 4 результата, `hasMoreAfter` становится `false`.

**Исправление:** полный устойчивый порядок и составной курсор `(timestamp, eventId, тип/ID вхождения)`; для поиска нескольких документов добавить `documentId`. Проверить одинаковые даты на обеих границах, комбинацию выполненных и планируемых событий и повторяемые вхождения. Сбрасывать/пересчитывать результаты при изменении документа и набора событий, чтобы идентификаторы другой вкладки не интерпретировались как прежние результаты.

### F11. Идентичность проекта и счётчики ссылок не согласованы с событиями

**Место:** [ProjectsStore.ts](../src/6-entities/Projects/ProjectsStore.ts), строки 62–81, 94–101, 118–135; [SingleEventManager.ts](../src/6-entities/Events/SingleEventManager.ts), `delete`, `update`; [RepeatableEventManager.ts](../src/6-entities/Events/RepeatableEventManager.ts), операции удаления и разбиения серии.

- Проект переименовывается в списке проектов, но `event.project` остаётся старым. В сохранённом JSON появляются проект `Beta` и событие со ссылкой `Alpha`. При следующей загрузке старый проект будет восстановлен из имени события.
- Счётчик `events` увеличивается при добавлении, но не уменьшается при удалении. В воспроизведении после удаления единственного события счётчик проекта остался 1: удалить пустой проект нельзя.
- `projectId` — индекс массива. Удаление проекта без событий перед проектом с событиями сдвигает индексы и нарушает ссылки на стили. Наличие счётчика не защищает от такого сдвига.

**Исправление:** стабильный ID проекта в модели и DTO, независимый от имени и позиции. Переименование меняет только имя. Ссылки и число использований получать из согласованного индекса событий либо обновлять в одной доменной транзакции. Удаление и разделение повторяемых событий также должны поддерживать инварианты. Для старых файлов нужна миграция ссылок по имени.

### F12. Баланс может обходить десятки тысяч дней на каждый запрос

**Место:** [EventsCache.ts](../src/6-entities/EventsCache/EventsCache.ts), строки 47–51, 185–193, 223–230, 243–251.

При отсутствии завершённых событий `lastActualBalanceDate` равен 0. `getPlannedBalance` передаёт его как начало интервала, и цикл идёт от Unix epoch до запрошенного дня с шагом 86400. В локальной проверке одного значения для 31.10.2026 выполнено **20 757 итераций** даже с подменённой пустой обработкой дня. Реальная обработка ещё перебирает события и заполняет кэш. Для UTC+3 начало такого интервала также не совпадает с локальным началом дня.

Календарь строит 21 неделю, поэтому стоимость на холодном кэше умножается на множество дневных расчётов. Это измерение числа итераций, а не замер задержки UI на пользовательском устройстве.

`getFirstPlannedEventDate` дополнительно возвращает 0, если нет одиночных планируемых событий, даже при наличии повторяемых; среди одиночных использует первый элемент без поиска минимума. Начальная загрузка не гарантирует нужную сортировку для всех этих предположений.

**Исправление:** ограничить расчёт фактическим диапазоном событий, хранить накопленные суммы/контрольные точки и вычислять периодические поступления без полного обхода истории. Кэши с числовыми датами представлять через `Map`, установить предел памяти и правила инвалидирования. Исправить вычисление первой даты для пустых, только повторяемых и несортированных наборов. Добавить тест на число выполняемых операций, а профилирование UI провести отдельно.

## 7. Интеграции и UI

### F13. Ошибки OAuth и API могут оставлять Promise незавершённым

**Место:** [gapi.ts](../src/7-shared/services/gapi.ts), строки 13–31, 91–104, 132–150.

В `prom` обработчик ошибки читает `err.result.error.code` без проверки структуры. Если внешний вызов отклонён обычным `Error`, внутри `.catch` возникает ещё одна ошибка до вызова внешнего `reject`. Обёртка, ожидаемая вызывающим кодом, остаётся pending; внутренний rejected Promise не возвращается наружу.

У token client отсутствует `error_callback` для закрытого/заблокированного popup. Общий `pendingLoginPromise` может не завершиться и блокировать следующие попытки входа. Google описывает эти ошибки отдельно от OAuth-ответа в [Handle Errors](https://developers.google.com/identity/oauth2/web/guides/error).

**Исправление:** убрать лишний `new Promise` вокруг уже асинхронного API, использовать `async/await`, нормализовать `unknown`-ошибки. Реализовать `error_callback`, гарантированную очистку pending-состояния во всех исходах, ограничение времени ожидания и возможность повторить операцию. Не считать любой `403 PERMISSION_DENIED` доказательством истёкшего токена: это может быть запрет доступа к конкретному ресурсу.

### F14. Погодные данные накапливаются, ошибки сети обрабатываются неполно

**Место:** [WeatherStore.ts](../src/5-features/Weather/WeatherStore.ts), строки 94–122; [openweathermap.ts](../src/7-shared/services/openweathermap.ts), `getForecast`.

`loadForecast` очищает `data1d`, но не `data3h`, поэтому повторная загрузка добавляет те же интервалы заново. Вокруг запроса нет `try/catch`: при сетевом отказе состояние остаётся `pending`. `getForecast` не проверяет `response.ok` и структуру JSON; тело ошибки может дойти до `f.list.forEach`. Объявленный статус `error` не используется в этой ветке.

Граница дня проверяется через `d.dt > t + 86400`, поэтому прогноз ровно на границе попадает в предыдущий день. Один `if` также не покрывает произвольный разрыв дат.

**Исправление:** собирать новый проверенный снимок в локальных переменных и целиком заменять оба массива; явно обрабатывать HTTP/сетевые ошибки и показывать возможность повтора. Группировать по вычисленному началу дня в выбранном часовом поясе. Защититься от устаревшего ответа после смены локации.

### F15. Базовые компоненты нарушают ожидаемые контракты UI

**Места:** [Button.tsx](../src/7-shared/ui/Button/Button.tsx), строки 13–34; [ListItem.tsx](../src/7-shared/ui/List/ListItem.tsx), строки 13–41; [TextButton.tsx](../src/7-shared/ui/Button/TextButton.tsx); [Time.tsx](../src/7-shared/ui/Time/Time.tsx), строки 15–22; [Dialog.tsx](../src/7-shared/ui/Dialog/Dialog.tsx); [Modal.tsx](../src/7-shared/ui/Modal/Modal.tsx).

- `Button` и `ListItem` извлекают `disabled`, но не применяют его ни к DOM, ни к обработчику. В отличие от них, `TextButton` признак учитывает. Компоненты с похожим API ведут себя по-разному.
- У кнопок задан `tabIndex={-1}`, что исключает их из обычного обхода клавишей Tab. Кликабельный `li` не получает клавиатурного поведения автоматически.
- У самописных модальных окон нет реализации управления фокусом, возврата фокуса, обработки Escape, `role="dialog"`/`aria-modal` и привязки доступного заголовка.
- `Time` не отменяет таймер и созданный интервал. Повторное монтирование оставляет лишние обновления. `Dialog`/`Modal` не отменяют таймер скрытия: быстрое повторное открытие может быть перекрыто старым таймером через 300 мс.

**Исправление:** опираться на семантику HTML, типизировать обёртки стандартными атрибутами кнопки, унифицировать disabled и клавиатурное поведение. Для модального примитива использовать корректно реализованный native dialog либо проверенный доступный компонент. Добавить cleanup таймеров и тесты быстрого закрытия/открытия. React прямо описывает цикл setup/cleanup эффектов в [useEffect](https://react.dev/reference/react/useEffect); [StrictMode](https://react.dev/reference/react/StrictMode) полезен для обнаружения таких ошибок в разработке.

### F16. Публикуется слишком широкая папка, отсутствуют обязательные проверки CI

**Место:** [.github/workflows/build.yml](../.github/workflows/build.yml), шаги Install dependencies / Build / Upload Pages artifact.

Workflow запускается только на push в `master`, выполняет `npm ci` и сборку, затем передаёт в Pages `path: .`. После установки в корне присутствуют исходники, документация, конфигурации и `node_modules`. Состав публикации не ограничен выходом приложения. Это вывод из workflow, а не проверка текущего публичного сайта. Исключения скрытых файлов в действии загрузки не превращают корень репозитория в корректный production-каталог; механизм упаковки виден в [исходниках upload-pages-artifact](https://github.com/actions/upload-pages-artifact/blob/v3/action.yml).

Тесты и линтер в workflow не запускаются, а отдельного PR-gate нет. Сборка через `ts-loader` сейчас проверяет типы, но не заменяет эти проверки.

**Исправление:** создавать отдельный каталог публикации, содержащий `index.html`, бандлы и необходимые favicon; загружать только его. Добавить CI на pull request и push: чистая установка → typecheck → lint-check → tests → build. Развёртывание должно зависеть от успешной проверки. Сохранить минимальные permissions и существующее разделение build/deploy.

### F17. В коде логируются токены, а ключ API лишь обфусцирован

**Место:** [gapi.ts](../src/7-shared/services/gapi.ts), строки 96, 158, 301–310; [scripts/encrypt.js](../scripts/encrypt.js); [webpack.config.cjs](../webpack.config.cjs), Dotenv.

В консоль выводятся полный `tokenResponse` и `token.access_token`. Это ненужное распространение credential через отладочные логи. Client ID по природе публичен и не должен классифицироваться как секрет только потому, что берётся из переменной окружения.

**Исправление:** удалить вывод access token и редактировать чувствительные поля диагностических событий. Уточнить назначение ключей, разделить переменные Google API и OpenWeatherMap, документировать разрешённые origins/API, ограничения и квоты. Если ключ должен оставаться секретным, вынести соответствующую операцию на доверенную серверную сторону; переименование переменной или другое шифрование внутри бандла проблему не решит.

В рамках аудита ключи не декодировались, их действительность и настройки ограничений не проверялись. История Git на наличие секретов полностью не сканировалась. Наличие `.env` в рабочей папке не является доказательством его публикации.

### F18. Апостроф в имени файла ломает поисковый запрос Drive

**Место:** [GoogleApiService.ts](../src/7-shared/services/GoogleApiService.ts), строка 225.

Запрос строится как `name = '${name}'`. Имя вроде `John's plan.json` меняет синтаксис `q`, поэтому обычное сохранение нового файла может завершиться ошибкой. Это проблема языка запросов Drive; она не означает SQL-инъекцию или обход разрешений Google.

**Исправление:** один helper экранирования обратной косой черты и одинарной кавычки для строковых литералов Drive, с тестами на оба символа и их сочетания. ## 8. Архитектура и современные практики

### Что уже сделано удачно

- Включён TypeScript `strict`, проверка типов проходит.
- Есть lockfile и установка `npm ci` в CI.
- `DocumentStoreManager` выделяет отдельные пары сторов событий/проектов на документ; провайдер `IEventsStoreProvider` уменьшает прямую связанность кэша.
- DTO и модели событий разделены через мапперы; расписания вынесены в отдельную библиотеку с большим набором проверок.
- Сборка компонентов и сервисов сосредоточена в `root.ts`, экземпляры передаются через React Context.
- Новый подход с базовым снимком, локальными изменениями и операциями в модели синхронизации уже намечен. Его стоит завершить и проверить, а не заводить третью параллельную схему.

### Завершить переход к единому состоянию документа

Сейчас одновременно существуют `session.state.isDirty/isLoading/isSaving/syncStatus/error`, `session.sync`, `session.operation`, отдельный `session.error` и `operationToken`. Код то пишет legacy-флаги напрямую, то пересчитывает их селекторами. Например, статус `syncing` записывается в старое поле, но `operation` остаётся `idle`; следующая синхронизация полей может потерять смысл операции.

Предлагаемая ответственность:

| Составляющая | Ответственность |
| --- | --- |
| Доменное содержимое | Проекты, события, стабильные ID и локальная версия |
| Состояние синхронизации | Последний подтверждённый базовый снимок/серверная версия, необходимость удалённой проверки |
| Операция | idle/opening/saving/checking/pulling, токен и ошибка конкретной операции |
| Селекторы UI | Dirty, возможный конфликт, доступность команд и подписи; вычисляются из предыдущих частей |
| Репозиторий хранения | Проверка входных данных, чтение/запись Drive и локального снимка |
| Сервис команд | Сохранить документ по ID, разрешить конфликт, закрыть с согласованным результатом |

Старая модель может оставаться адаптером на время миграции, но должна обновляться только из единого источника. Прямые записи в неё нужно последовательно убрать и затем удалить сам адаптер. Явную машину переходов можно реализовать средствами TypeScript; отдельная библиотека нужна только при оправданной сложности.

### Уменьшить связанность и побочные эффекты

`SaveToDriveStore` зависит от `MainStore` из слоя `app`, чтобы отправить уведомление. Компоненты разных слоёв зависят от общего контекста приложения; классы часто принимают конкретный `GoogleApiService`. Поэтому соответствие Feature-Sliced Design преимущественно структурное: направление зависимостей не контролируется.

Практический шаг — небольшие интерфейсы у потребителей (`DriveRepository`, хранилище снимков, уведомление о сохранении), передаваемые из composition root. Не нужно перемещать весь корневой контракт в `shared`: это сохранит связанность под другим именем. Для соблюдения правил импорта добавить автоматическую проверку границ только после согласования самих границ.

`root.ts` вызывает `mainStore.init()` при импорте. Это затрудняет тесты, повторный запуск и освобождение ресурсов. Предпочтительнее `createAppServices()` плюс явные `start()`/`dispose()`. Доменным классам следует возвращать результат операции вместо `alert`, чтобы UI мог показывать ошибки и тестировать их без браузерных побочных эффектов.

### Сделать изменения и производные данные наблюдаемыми последовательно

`EventsStore` и `EventsCache` используют собственные callback и обычные массивы; интерфейс дополнительно поддерживается через `forceUpdate`, `UIStore.mustForceUpdate` и эффекты. Это повышает риск пропущенной инвалидизации. Нужно выбрать и закрепить один механизм уведомления об изменении доменных данных: observable-состояние/локальная версия документа и зависимые computed/кэши либо чёткий поток доменных событий с подписками и dispose. Наличие MobX в приложении позволяет сделать это без второго глобального state manager.

Мутации после `await` в `openFromDrive`, синхронизации и восстановлении местами не заключены в action. `makeAutoObservable` не превращает все продолжения асинхронной функции в одну транзакцию. Следует группировать применение результата в `runInAction` или использовать `flow`; проверить поведение с `enforceActions` в разработке. Семантика описана в [MobX actions](https://mobx.js.org/actions.html). Это рекомендация по корректности реактивного состояния, а не утверждение, что каждый такой участок сейчас бросает исключение.

### Усилить типы на реальных границах

`strict` полезен, но не проверяет внешний JSON. Приоритетнее runtime-валидация и `unknown` в обработчиках ошибок, чем массовое устранение всех `any` ради метрики. `StoreContext` создаётся через `{} as IRootStore`, поэтому отсутствие провайдера превращается в позднюю ошибку доступа к полю: лучше nullable context и `useStores()` с явной проверкой.

После исправления критических сценариев постепенно включить `noUncheckedIndexedAccess` и при необходимости `exactOptionalPropertyTypes`, убрать ненужные `!`, отделить tsconfig приложения и тестов. Первый флаг позволяет видеть возможный `undefined` у индексных обращений: [TypeScript](https://www.typescriptlang.org/tsconfig/noUncheckedIndexedAccess.html).

В линтере отсутствуют проверки зависимостей React hooks и значимая часть правил TypeScript для Promise. Добавить их постепенно после настройки type-aware linting. `lint` сейчас выполняет `--fix`; для CI использовать только немутирующий `lint-check`, форматирование оставить отдельной командой.

### Даты, суммы и формат файла

`DateTime` сознательно использует фиксированный offset `+3` и арифметику дней по 86400 секунд, не учитывая исторические изменения часовых поясов. Для личного календаря в одном фиксированном поясе это допустимый контракт. Если нужны другие регионы, DST или совместная работа, нужно хранить календарную дату отдельно от абсолютного момента, явно задавать IANA timezone и определить правила повторений. Переход на другую библиотеку дат без такого решения лишь перенесёт неоднозначность.

В форме даты проверяются регулярным выражением, допускающим, например, 31 февраля, а связь `end > start` не закреплена общей доменной валидацией. Эти проверки должны применяться и к импортированным файлам.

Поступления/списания считаются через `number`. Если нужен точный учёт денежных сумм, нужно определить масштаб и округление и использовать целые минимальные единицы либо подходящее десятичное представление. Для приблизительного планирования ресурсов это может быть необязательным изменением. Это проектное решение, не вывод о неверности каждого текущего баланса.

### Обновления и инструменты

Обновлять зависимости следует отдельными небольшими изменениями после появления защитных тестов для сохранения. Возраст React 18 или webpack сам по себе не делает приложение некорректным; переход на Vite или React следующего major не исправит найденные ошибки.

Убрать либо восстановить старый Karma-путь: `karma.conf.js` использует CommonJS `require` при `type: module` и ссылается на `webpack.config.test.js`, которого нет — в репозитории файл `.cjs`. В активных npm scripts используется Jest, поэтому это поломанный запасной путь, а не причина отказа `npm test`.

Также стоит удалить дублирующий `.eslintrc.json` после проверки актуального flat config, унифицировать окончания строк и формат конфигураций, зафиксировать версию Node для локальной работы и описать переменные окружения в безопасном `.env.example`. В `README` сейчас отсутствуют инструкции установки, запуска, проверок, восстановления документов и модель хранения.

## 10. Обязательная регрессионная матрица

| Сценарий | Ожидаемый результат |
| --- | --- |
| Новый изменённый документ → закрыть → «Сохранить» | Открывается «Сохранить как»; отмена сохраняет вкладку |
| Существующий документ → ошибка записи → закрытие | Вкладка и локальные изменения остаются |
| Изменение A во время сохранения A | Сохраняется отправленный снимок; более новые изменения остаются dirty |
| Начать сохранение A → активировать B → успех/ошибка | Меняется только состояние A |
| «Сохранить как» A → сменить вкладку/отредактировать A | Метаданные относятся к A; новые правки не помечаются сохранёнными |
| Начать открытие A → закрыть A до ответа | Устаревший ответ игнорируется, необработанных исключений нет |
| Одновременные сохранения одного документа | Есть заданный порядок; старый ответ не отменяет результат нового |
| Drive изменён другим клиентом | Конфликт определяется относительно базовой серверной версии |
| Перезапуск без GAPI/сети | Локальная сессия восстанавливается независимо от Drive |
| Перезапуск во время сохранения | Временные операции сброшены, локальные изменения сохранены |
| Конфликт имени → overwrite / rename / cancel | Все три пути завершаются определённым результатом |
| Смена имени события `Aa` → `BB` | Изменение определяется |
| Более четырёх совпадений в один день | Все результаты достижимы в обоих направлениях |
| Переименование/удаление проекта, удаление последнего события | Ссылки и счётчики корректны до и после перезагрузки |
| Календарь без завершённых событий | Нет обхода пустой истории с Unix epoch |
| Некорректный JSON, событие `null`, невозможная дата | Понятная ошибка до изменения существующего состояния |
| Ошибка квоты/запрета localStorage | Видимая ошибка; приложение не заявляет об успешной локальной записи |
| Закрытие OAuth-popup, ошибка API без `result.error` | Операция отклонена и доступна повторная попытка |
| Две загрузки погоды, HTTP-ошибка, ответ старой локации | Нет дубликатов/зависшего pending/подмены новой локации |
| Tab, Enter, Escape, быстрое повторное открытие модального окна | Предсказуемый фокус и отсутствие действий disabled-компонентов |

Для доменной логики достаточно unit-тестов. Гонки нужно проверять управляемыми Promise, а не произвольными задержками. Для контрактов Google API необходимы тесты адаптера с реальной формой ответа и проверкой исходящих полей/параметров. Для закрытия вкладок, модальных окон и OAuth нужен небольшой набор интеграционных/браузерных сценариев.

### Порядок обновления зависимостей

В первую очередь обновить совместимые транзитивные версии, сборщик и стек dev-server; затем устранить старую Karma-цепочку и обработать оставшиеся находки тестового/линтерного стека. Среди high-находок есть `webpack-dev-middleware`, `ws`, `launch-editor`, `serialize-javascript`, `postcss`, `node-forge`, `minimatch` и другие; полный перечень и пути находятся в JSON.

`fixAvailable` нельзя трактовать как готовый безопасный план миграции. Отчёт предлагает, например, `webpack-dev-server@6.1.0`, откат Jest до `29.7.0`, `@eslint/js` до `9.39.5`, а `eslint-plugin-prettier` до `2.7.0`. Это предложения resolver, а не проверенная совместимость. Для семи записей автоматического исправления нет (`fixAvailable: false`), в том числе для частей typescript-eslint и Karma. Нужны обновление родителя, удаление неиспользуемой цепочки или документированное решение по оставшемуся риску; массовый `npm audit fix --force` не рекомендуется.

Помимо локальных дефектов F01–F18 следует считать отдельной приоритетной задачей **D01: устранение critical/high-находок dev-дерева и проверка артефакта публикации**. Конкретные обновления должны сопровождаться новой установкой, проверкой типов, тестами, сборкой и повторным аудитом.
