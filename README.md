# Projector

Веб-приложение для планирования событий (задач) и ресурсов.

Пример приложения по ссылке: https://zimazky.github.io/projector/

Окружение: Node.js **24.12.0**, npm **11.12.1**; установка — `npm ci`.
Запуск — `npm start`, затем открыть `http://127.0.0.1:8080/index.html`.
Для другого порта в PowerShell: `$env:PROJECTOR_DEV_PORT = '8081'` перед запуском.

Проверки: `npm run typecheck`, `npm run lint-check`, `npm test -- --runInBand`, `npm run build`.

Сборка зависимостей находится в `src/1-app/root.ts`: `createApplication()` создаёт сторы без загрузки Google API и чтения локальной сессии. Точка входа `src/1-app/index.tsx` явно вызывает `start()` и передаёт `application.stores` в `StoreProvider`; компоненты получают их через `useStores()`. При освобождении экземпляра вызывается `dispose()` (также в обработчике HMR): снимаются подписки и таймеры, отменяются загрузчики Google/OAuth и погода, поздние ответы Drive и восстановления игнорируются. Уже начатые локальные записи завершаются, сохранённая сессия не удаляется. Оба метода идемпотентны; после dispose создаётся новый экземпляр. Переданный фабрике GoogleApiService принадлежит этому экземпляру и освобождается вместе с ним. Браузерный транспорт Google использует глобальные GIS/GAPI; одновременная работа нескольких активных приложений в одном окне не предусмотрена. Подробности — в [отчёте PR 16](docs/remediation_pr16_2026-11-01_ru.md).

Полный прогон с JSON-отчётами: `npm run verify:baseline`.
Проверки в настоящем браузере: `npm run browser:install`, затем `npm run test:e2e`.
Интерактивный запуск: `npm run test:e2e:ui`; отчёт: `npm run test:e2e:report`.
Сценарии и изоляция Google API описаны в [инструкции Playwright](docs/browser_testing_ru.md).
Чистая установка, воспроизводимые тесты и резервный снимок описаны в [отчёте этапа 0](docs/remediation_stage0_2026-10-31_ru.md).

Артефакт для GitHub Pages: `npm run build:pages`, результат — `artifacts/pages`.
Изменения сохранения и закрытия документов описаны в [отчёте этапа 1](docs/remediation_stage1_2026-10-31_ru.md).

Обновление зависимостей, проверки dev-server и оставшиеся advisory — в [отчёте этапа 2](docs/remediation_stage2_2026-10-31_ru.md).

Команды по ID, защита от устаревших ответов и локальные версии описаны в [отчёте этапа 3](docs/remediation_stage3_2026-10-31_ru.md).

После [S01](docs/remediation_s01_2026-11-01_ru.md) **«Сохранить» обновляет тот же файл Drive**, сохраняя ID, имя и ссылку. Перед записью проверяются версия и содержимое относительно известной базы; обновление использует `If-Match` с ETag Drive v2. При конкурентном изменении сервер отклоняет запись, приложение предлагает выбрать локальную или удалённую версию. Ошибка сети оставляет локальные данные неподтверждёнными. «Сохранить как...» создаёт отдельный файл. Для прежних файлов «(версия …)» обычное сохранение обновляет текущий связанный файл; возврат к другому файлу выполняется его явным открытием. Прежняя политика отдельных версий описана исторически в [отчёте этапа 4](docs/remediation_stage4_2026-10-31_ru.md).

Живую проверку условной записи можно повторить командой `npm run verify:drive`, открыв показанный локальный адрес вместо приложения. Проверка использует новые тестовые файлы, проверяет устаревший ETag, повторное сохранение и два клиента, затем перемещает тестовые файлы в корзину. Отчёт без токенов записывается в `artifacts/drive-write-live/result.json`. Обычный сервер и проверку нельзя запускать на одном порту одновременно.

На [этапе 5](docs/remediation_stage5_2026-11-01_ru.md) локальная сессия восстанавливается независимо от Google API. После [PR 12](docs/remediation_pr12_2026-11-01_ru.md) документы Drive используют `schemaVersion: 2`: проекты содержат стабильный `id`, события ссылаются на него через `projectId`. Переименование не меняет принадлежность событий. Локальные снимки и экспорт сессии используют отдельный формат `schemaVersion: 3`, содержащий данные и `sync` без дублирующих флагов. Документы без версии/v1 и сессии без версии/v1/v2 читаются и мигрируют на копии. Перед заменой старой локальной сессии сохраняется исходник; при ошибке транзакции IndexedDB остаются прежние данные. Версия самой базы IndexedDB остаётся 1. Старые сборки не понимают новые форматы; для отката нужен сохранённый исходник с учётом последующих правок.

После сообщения о переполнении localStorage [хранение перенесено в IndexedDB](docs/indexed_storage_migration_2026-11-01_ru.md). При доступном IndexedDB исходные записи и новая сессия записываются в одной транзакции; прежний localStorage не удаляется и больше не используется для новых снимков. Если IndexedDB отсутствует в браузере, остаётся прежний localStorage-путь. Ошибка доступа к существующему IndexedDB не приводит к молчаливому чтению устаревшей локальной копии.

При сбое приложение показывает причину и позволяет экспортировать актуальную сессию и исходные данные. В меню «Импортировать сессию из файла» можно открыть `projector-session.json`: восстановленные вкладки добавляются к существующим и получают суффикс «(восстановлено)». Архив исходных записей `projector-recovery-source.json` служит для ручного восстановления, этот пункт меню принимает экспорт сессии. Дождитесь исчезновения «Сохраняется локальная копия…» перед перезагрузкой. При незавершённой или неудачной записи приложение предупреждает о закрытии страницы.

Для выяснения причины локальной ошибки нажмите «Повторить локальное сохранение» и раскройте «Подробности ошибки». Тип исключения, хранилище, операция и размеры описаны в [инструкции диагностики](docs/local_storage_diagnostics_ru.md). Полноценный запуск страницы без сети и восстановления собственных JS/CSS из кэша пока не гарантируется.

Старые записи после миграции можно убрать через меню «Очистить старые локальные записи». Команда сначала подтверждает текущую сессию и архивирует исходники в IndexedDB, затем удаляет совпадающие с архивом записи localStorage. Неизвестные ключи и архивы остаются. Через «Экспортировать резервные снимки» архив доступен для скачивания. [Порядок и проверки очистки](docs/local_storage_cleanup_2026-11-01_ru.md).

После [PR 13](docs/remediation_pr13_2026-11-01_ru.md) баланс считается на начало местного дня из накопленных сумм и числа повторяемых вхождений. Пустая история не вызывает обход дней с 1970 года; дневные кэши календаря ограничены и сбрасываются при смене документа или его данных.
